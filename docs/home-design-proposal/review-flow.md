# 無料開放から評価につなげる追加提案

[確認用画像](review-flow.png)。2026-11-06、バージョンを更新しない利用者にも機会を設けたいという要望を受け、最短10日間隔へ改訂した提案の記録。その後、承認を受けて実装した。[実装内容・検証記録](../home-study-release/README.md)を参照。以下の「現行」「未変更」は提案時点を示す。

## 狙い

無料で使えることを明確に伝え、教材が役立つ体験を重ねてもらう。学習の区切りで率直な評価を残しやすくする。開発者が実際に図解や解説を改善していることと、感想が次の受験者にも役立つことを伝える。無料ライセンスは評価の有無に関係なく維持する。

## 現在のコードで確認できたこと

- `feedbackRules.ts`：初回利用日を1日目として3日目以降。その後は前回依頼から7日以上。前面で30秒以上の学習が対象。
- `studyFeedback.ts`：対象の学習画面を離れ、他の学習画面が開かれていないときに400ms待って判定。
- `feedback.ts`：Appleの標準評価APIを使用。アプリ側では365日間に最大3回の「呼び出し」を記録する。実際に画面が表示された回数や評価が投稿された回数ではない。
- 条件が毎回成立すると、3日目・10日目・17日目頃にアプリ側の3回分を使い切り得る。その後も要望メール画面の対象にはなる。
- 評価APIの呼び出し後、`App.tsx` の全画面のご意見・ご要望画面へつなぐ構成。評価とメールのお願いが連続する可能性がある。
- 得点や満足度による選別は現状もない。設定の「アプリを評価する」はApp Storeの投稿画面への直接リンク。

## 提案する導線

1. ホームには小さな「無料ライセンス適用済み」表示を置く。教材と模試をすべて使えることを伝える。無料適用の直後には評価を依頼しない。引き継ぎ制限などの詳細は既存の利用権説明で確認できるようにする。
2. 普段のホーム／学習終了時に、教材・用語・クイズの取り組みを表示する。評価依頼のためだけの確認ポップアップにはしない。
3. 利用経験を重ねた後、学習の区切りにApple標準評価APIを呼ぶ。表示されなくても別の独自評価画面やApp Storeを自動で開かない。
4. 設定の「このアプリについて」に開発者の短いメッセージと常設のApp Storeリンクを置く。「ご意見・ご要望」も全員に並べて表示する。
5. 評価依頼の直後に要望メール画面を自動表示しない。問い合わせは常設の入口から送れる。自動のメール依頼を残すなら、評価とは別の日・別の機会にする。

## 表示タイミングの変更案

現行の週1回方式から、最短10日間隔と新たな学習経験を条件にする方式へ変更する案。まだ設定は変更していない。10日経過は標準APIを呼ぶ候補日であり、画面を必ず表示する約束ではない。

- 初回利用から3日目以降。
- 2日以上にわたり、対象となる学習セッションを3回以上経験。
- 教材・用語・問題のいずれかを前面で30秒以上学び、その学習を終了したとき。
- 模試は途中離脱も対象にできる。全問の完了や合格を条件にしない。試験中・問題を読んでいる途中には表示しない。
- 学習一覧やホームに戻って約2秒間、遷移や他の操作がないことを確認する。
- 再依頼の候補は前回の標準API呼び出しから10日以上経過した後。前回以降も2日以上にわたり対象学習を3回以上行い、その学習を終了した区切りを選ぶ。日数が過ぎただけでは起動直後に依頼しない。
- アプリ独自の「同じバージョンは1回」「更新後のみ」「30日以上」の条件は、この案では設けない。ただしAppleは同じバージョンで繰り返し依頼しないことを推奨しているため、この案はその推奨とは異なる。審査上問題ないと保証するものではない。
- 現行の「API呼び出し3回で365日間停止」は実表示数を表さないため見直す案。実際の表示回数と投稿済みの扱いはStoreKitに任せる。未評価者への標準画面は365日間に最大3回で、表示されないこともある。独自ポップアップや自動でApp Storeを開く動作で補わない。
- OS側の表示制限・ユーザーによる無効化を尊重する。API呼び出し・実表示・評価投稿を同じ実績として集計しない。
- 利用者が常設リンクからApp Storeを開いた場合も、その日から最低10日間は自動依頼を控える案。リンクを押しただけで「投稿済み」とは記録せず、永久停止の根拠にもしない。

学習セッションの件数や複数日利用の記録は追加実装が必要。学習済みの表示は単なる画面表示時間と混同しない。画像の実績はすべてサンプル。

## 評価と発見につながる施策

- 初回3日目以降の学習の区切りで、標準画面から少ない操作で率直な評価を残せるようにする。
- 設定に常設する評価リンクと、次の受験者にも感想が役立つことを伝える短い説明を整える。無料権利は評価と切り離す。
- 教材・用語・模試を体験した人を広く対象にし、点数や満足度による選別をしない。
- ストアのタイトル・サブタイトル・キーワードの検索語との一致、実際の教材や図解が伝わるスクリーンショットも改善対象とする。評価数だけで検索順位が決まるわけではない。
- 変更前後の新規評価数・平均評価・検索経由の表示数・ダウンロード率を週単位で確認する。API呼び出し数から投稿率を推計しない。Appleが個々のユーザーの投稿有無をアプリへ返す前提にしない。

10日間隔が評価を最も増やすと確認できたわけではなく、今回の利用期間と要望に合わせた検証案である。

## Appleの一次資料と設計上の境界

- [App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)：3節は報酬付き・選別されたレビュー等による操作を禁じる。3.2.2(x)は利用条件としての評価要求を禁じる。5.6.1は評価依頼に提供APIを用い、独自の評価依頼ポップアップを認めない旨を記載している。
- [Requesting App Store reviews](https://developer.apple.com/documentation/storekit/requesting-app-store-reviews)：利用経験を積んだ区切りで依頼し、起動直後や作業中の中断を避ける。システム表示は365日間に最大3回で、ユーザーが無効化する場合もある。
- [RequestReviewAction](https://developer.apple.com/documentation/storekit/requestreviewaction)：標準APIは表示されない場合がある。ボタン操作からは標準APIに依存せず、設定に常設のApp Storeリンクを用意できる。`action=write-review` を付ける方法が示されている。
- [Apple WWDC22](https://developer.apple.com/videos/play/wwdc2022/10007/)：同じバージョンで繰り返し依頼しないことを推奨している。
- [App Store search](https://developer.apple.com/app-store/search/)：検索順位には名称・サブタイトル・キーワード等の関連性と、ダウンロード・評価・レビュー等が影響する。表示数やダウンロード率をApp Analyticsで確認できる。

無料権利を評価の報酬にする、★5を指定する、不満を持つ人だけ問い合わせに振り分ける、架空の利用者数・開発事情を使う、評価しないと利用しにくくする、といった導線は設けない。評価数の増加を保証するものでもない。画像内の中央の青枠はOS画面への遷移を説明する模式図で、実際のアプリUIには配置しない。
